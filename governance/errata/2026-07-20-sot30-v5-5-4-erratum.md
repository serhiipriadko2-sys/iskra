# Erratum — SoT30 v5.5.4

Date: 2026-07-20
Package: `dist/SoT30_v5.5.4.zip` (sha256 `235abf73040427bbb54016acce880a023db32aab3b7be5d1fc77fc3b1f486772`)
ADR: ADR-20260720-02 (`accepted`)
Status: open — package is **immutable**; byte-level fixes deferred to a future version (v5.5.5).

This erratum records defects discovered **after** v5.5.4 was built and merged (PR #289). The package bytes are not changed. Verifier/build-script/receipt fixes ship in PR-C (`fix/sot30-v554-verifier-hardening`); genuine in-package byte fixes are deferred to v5.5.5.

## E1 — `MANIFEST.json` `generated_from` mislabel (in-package)

`support/MANIFEST.json` records `"generated_from": "canonical_git_blobs"`. The v5.5.4 build (`tools/build_sot30_release.py`) actually read the **release-tree working files** via `open()`/`read_bytes()`; it never invoked `git show`/`git cat-file` and took no commit SHA as a source ref. (The label was inherited from the v5.5.3 build, which genuinely extracted `git show 31340c5:<path>`.)

- **Impact:** provenance-label inaccuracy only. The bytes hashed are the committed release-tree bytes; on a clean tree those equal the git blobs, so no content is wrong — but the *method* claim is false for v5.5.4.
- **Disposition:** in-package (support/MANIFEST.json is inside the ZIP) → **byte-fix deferred to v5.5.5**. In v5.5.5 the build will either truly extract from an explicit commit/blob source, or label `generated_from: release_tree_working_bytes`. PR-C fixes the build script for future releases and this erratum records the honest status now.

## E2 — ZIP root naming inconsistency (in-package, cosmetic)

The v5.5.4 ZIP top-level directory is `SoT30_5.5.4/` (missing the `v`), whereas v5.5.3 shipped `SoT30_v5.5.3/`. Caused by `build_sot30_release.py` deriving `root = f"SoT30_{version[1:]}"`.

- **Impact:** cosmetic; extraction and `sha256sum -c` are unaffected (paths are relative to the single root). The hardened verifier checks "exactly one top-level root" without hard-coding its name, so it passes.
- **Disposition:** in-package → **deferred to v5.5.5**; PR-C fixes the build script so future roots are `SoT30_v<version>/` consistently.

## E3 — Verifier proved weaker properties than its labels (fixed in PR-C, out-of-package)

An independent review (ISKRIV read-back) found `tools/verify_sot30_release.ts` enforced several checks as necessary-but-insufficient proxies:
- file-29 table / `MANIFEST.files` counted rows but did not assert the exact unique filename **set**;
- `changed ∪ unchanged` checked size, not equality with the actual filename set;
- T80 used a substring `includes()`, not a byte-equal extraction of the mirror region;
- ZIP check ran `sha256sum -c` but did not reject extra/undeclared entries or multiple roots;
- the "forbidden-content" scan covered only knowledge files with a few secret patterns, not the advertised `.env`/`node_modules`/cache/absolute-path/secret coverage across knowledge+support+audit+scripts;
- T88 searched for a retired string instead of comparing composition across the five surfaces.

- **Impact:** the shipped v5.5.4 package is well-formed (it passes the hardened verifier unchanged), but the build-time verifier *proved* less than it claimed.
- **Disposition:** **out-of-package** → fixed in PR-C (verifier + tests + honest QC/README/receipt qualifications). No package bytes change.

## E4 — Release-root receipts overstated some gates (fixed in PR-C, out-of-package)

`QC_REPORT.md`/`README.md`/`PACKAGE_RECEIPT.md` (which are **not** inside the ZIP) declared T88, T80 "raw-equal", and the secret scan as unqualified PASS. PR-C annotates these `[build-time proxy → hardened PR-C]` with a dated qualification rather than silently rewriting the shipped results.

- **Disposition:** out-of-package → corrected in PR-C.

## Not affected

- Knowledge files 00–29 content, `SHA256SUMS`, and the ZIP payload remain byte-identical to the merged v5.5.4.
- v5.5.3 remains the immutable historical release.
- No runtime, Supabase, or live-Project change.
