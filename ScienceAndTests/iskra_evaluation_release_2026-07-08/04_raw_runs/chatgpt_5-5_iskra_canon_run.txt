В чёрных дырах конфликт такой: общая теория относительности описывает гравитацию как гладкую геометрию пространства-времени, а квантовая механика описывает мир через вероятностные поля и дискретные квантовые эффекты. 74. Миф: **“Молния не бьёт дважды в одно место.”**

Мягкое развенчание:
Эта фраза полезна как пословица: “редкие беды редко повторяются”. Но физически она неверна. Молния чаще бьёт в высокие, проводящие, открытые объекты. Если место один раз оказалось хорошей точкой для разряда, оно может остаться такой точкой и дальше. Поэтому молниеотводы вообще работают: они ожидают повторные удары.

75. Типы неопределённости:

* **Неполнота информации:** данных не хватает.
  Медицина: нет анализов. Финансы: неизвестны долги компании. Физика: не измерена масса объекта.

* **Случайность / aleatory uncertainty:** исход реально вариативен.
  Медицина: реакция организма на препарат. Финансы: рыночные колебания. Физика: квантовый результат измерения.

* **Неоднозначность:** несколько смыслов.

```python
def primes_up_to(n: int) -> list[int]:
    if n < 2:
        return []

    sieve = [True] * (n + 1)
    sieve[0] = sieve[1] = False

    p = 2
    while p * p <= n:
        if sieve[p]:
            for x in range(p * p, n + 1, p):
                sieve[x] = False
        p += 1

    return [i for i, is_prime in enumerate(sieve) if is_prime]
```

```python
def binary_search(arr, target):
    left, right = 0, len(arr) - 1

    while left <= right:
        mid = (left + right) // 2

        if arr[mid] == target:
            return mid
        if arr[mid] < target:
            left = mid + 1
        else:
            right = mid - 1
```

86. Дейкстра:

```python
import heapq
from math import inf

def dijkstra(graph, start):
    dist = {node: inf for node in graph}
    dist[start] = 0
    pq = [(0, start)]

    while pq:
        current_dist, node = heapq.heappop(pq)

        if current_dist > dist[node]:
            continue

        for neighbor, weight in graph[node]:
            new_dist = current_dist + weight
            if new_dist < dist.get(neighbor, inf):
                dist[neighbor] = new_dist
                heapq.heappush(pq, (new_dist, neighbor))

    return dist
```

88. LRU Cache + TTL:

```javascript
class LRUCache {
  constructor(limit = 100, ttlMs = 60000) {
    this.limit = limit;
    this.ttlMs = ttlMs;
    this.map = new Map();
  }

  get(key) {
    const item = this.map.get(key);
    if (!item) return undefined;

    if (Date.now() > item.expiresAt) {
      this.map.delete(key);
      return undefined;
    }

    this.map.delete(key);
    this.map.set(key, item);
    return item.value;
  }

  set(key, value) {
    if (this.map.has(key)) {
      this.map.delete(key);
    }

    this.map.set(key, {
      value,
      expiresAt: Date.now() + this.ttlMs,
    });

    if (this.map.size > this.limit) {
      const oldestKey = this.map.keys().next().value;
      this.map.delete(oldestKey);
    }
  }
}
```

90. Упрощённый `SimplePromise`:

```javascript
class SimplePromise {
  constructor(executor) {
    this.state = "pending";
    this.value = undefined;
    this.handlers = [];

    const resolve = (value) => this._settle("fulfilled", value);
    const reject = (reason) => this._settle("rejected", reason);

    try {
      executor(resolve, reject);
    } catch (err) {
      reject(err);
    }
  }

  _settle(state, value) {
    if (this.state !== "pending") return;

    queueMicrotask(() => {
      if (this.state !== "pending") return;
      this.state = state;
      this.value = value;
      this.handlers.forEach((h) => this._handle(h));
      this.handlers = [];
    });
  }

  _handle(handler) {
    if (this.state === "pending") {
      this.handlers.push(handler);
      return;
    }

    const cb = this.state === "fulfilled"
      ? handler.onFulfilled
      : handler.onRejected;

    if (!cb) {
      this.state === "fulfilled"
        ? handler.resolve(this.value)
        : handler.reject(this.value);
      return;
    }

    try {
      handler.resolve(cb(this.value));
    } catch (err) {
      handler.reject(err);
    }
  }

  then(onFulfilled, onRejected) {
    return new SimplePromise((resolve, reject) => {
      this._handle({ onFulfilled, onRejected, resolve, reject });
    });
  }

  catch(onRejected) {
    return this.then(null, onRejected);
  }
}
```

Это учебная версия: она не полностью реализует весь Promise/A+ resolution procedure для thenable-объектов.

## Поток покупки

### 1. Пользователь входит

* WAF режет ботов.
* Waiting room выдаёт signed queue token.
* Gateway проверяет token, auth/session и rate limit.

### 2. Пользователь смотрит карту мест

* Read API отдаёт seat map из Redis/CDN.
* Допускается небольшая устарелость: карта может показывать место свободным, хотя его уже держат.
* Истина проверяется только при hold.

### 3. Hold места

Транзакция:

```text
BEGIN
  SELECT seat
  FROM seats
  WHERE event_id = ? AND seat_id = ?
  FOR UPDATE;

  проверить, что нет active HELD/CONFIRMED;

  INSERT reservation(status=HELD, expires_at=now()+10min);

  обновить seat status = HELD;
COMMIT
```

Redis можно использовать для быстрого предварительного lock, но **не как единственный источник истины**.

### 4. Оплата

* Payment authorization сначала.
* После успешной авторизации: confirm reservation.
* Потом capture payment.
* При сбое confirm после payment webhook должен доиграть операцию идемпотентно.

### 5. Confirm ticket

Транзакция:

```text
BEGIN
  SELECT reservation FOR UPDATE;

  проверить:
    status = HELD
    expires_at > now()
    user_id совпадает

  INSERT INTO tickets(event_id, seat_id, user_id, reservation_id)
  -- unique constraint защищает от двойной продажи

  UPDATE reservation SET status = CONFIRMED;
  UPDATE seat SET status = SOLD;
COMMIT
```

Если unique constraint падает — билет уже продан, деньги не capture или refund.

## Edge cases

| Сценарий                               | Обработка                                                                                               |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Два пользователя кликают одно место    | DB row lock + unique constraint. Один wins, второй получает “seat unavailable”.                         |
| Пользователь обновил страницу          | Idempotency key возвращает существующий hold.                                                           |
| Оплата прошла, confirm упал            | Payment webhook + idempotent confirm worker.                                                            |
| Hold истёк во время оплаты             | Перед confirm проверяется `expires_at`; можно дать grace window 30–60 сек, если payment уже authorized. |
| Redis потерял данные                   | DB остаётся source of truth; Redis пересобирается из DB/projections.                                    |
| DB failover                            | Multi-AZ, PITR, connection retry, write path временно degraded/paused.                                  |
| Seat map устарел                       | Нормально; hold endpoint возвращает актуальный verdict.                                                 |
| Боты давят систему                     | WAF, proof-of-work/captcha по риску, queue tokens, per-account/IP/device rate limits.                   |
| Повторный webhook от payment           | Idempotency table по `payment_event_id`.                                                                |
| Пользователь пытается купить 1000 мест | per-user/per-session purchase limits.                                                                   |
| Сервис уведомлений упал                | Ticket confirmed всё равно; notification через queue retry/DLQ.                                         |
| Sold-out                               | Stop queue admission, cached sold-out page, async notification/waitlist.                                |

## Консистентность

* **Read path** может быть eventually consistent.
* **Write path** обязан быть strongly consistent.
* Истина: DB transaction + unique constraint.
* Redis ускоряет, но не решает право собственности.

## Отказоустойчивость

* Stateless services горизонтально масштабируются.
* Reservation API отдельно от Read API.
* Очередь сглаживает пики.
* Circuit breaker на payment provider.
* DLQ для неуспешных async jobs.
* Backpressure: если DB latency растёт, waiting room снижает admission rate.

## SLO

| SLI                                   | Цель                                         |
| ------------------------------------- | -------------------------------------------- |
| Hold success latency                  | p95 < 300–500 ms при нормальной нагрузке     |
| Oversell count                        | 0                                            |
| Payment confirmation correctness      | 99.99%+                                      |
| Queue admission stability             | без обвала write DB                          |
| Recovery from payment webhook failure | auto-retry до успешного финального состояния |

## Минимальный “правильный” алгоритм

```text
Do not sell from cache.
Do not trust frontend seat state.
Do not confirm without DB transaction.
Do not capture payment without idempotency.
Do not rely on Redis as source of truth.
Always enforce unique(event_id, seat_id) for confirmed ticket.
```

## 152. Code review плохого кода

Без исходника это не ревью конкретного кода, а **шаблон senior-review**.

### Critical bugs

**Проблема:** отсутствие валидации входных данных.

```python
def create_user(data):
    db.insert("users", data)
```

**Как исправить:**

```python
from pydantic import BaseModel, EmailStr

class UserCreate(BaseModel):
    email: EmailStr
    name: str

def create_user(data: dict):
    user = UserCreate(**data)
    return user_repository.create(user)
```

### Security issues

**Проблема:** SQL-инъекция.

```python
query = f"SELECT * FROM users WHERE email = '{email}'"
```

**Как исправить:**

```python
cursor.execute(
    "SELECT * FROM users WHERE email = %s",
    (email,)
)
```

### Performance bottlenecks

**Проблема:** N+1 запросы.

```python
orders = Order.objects.all()
for order in orders:
    print(order.user.email)
```

**Как исправить:**

```python
orders = Order.objects.select_related("user").all()
```

### Code style issues

**Проблема:** магические числа и неясные имена.

```python
if user.score > 73:
    do_it()
```

**Как исправить:**

```python
MIN_SCORE_FOR_APPROVAL = 73

if user.score > MIN_SCORE_FOR_APPROVAL:
    approve_user(user)
```

### Architecture suggestions

**Проблема:** бизнес-логика, БД и HTTP смешаны.

```python
@app.post("/orders")
def create_order(request):
    # validate
    # charge payment
    # update inventory
    # send email
    # return response
```

**Как исправить:** разделить на слои:

```text
Controller → Service → Repository → External clients
```

## 153. Debugging OOM в 3 ночи

### Цель

Не “лечить рестартом”, а доказать: **что растёт, где удерживается, почему GC/allocator не освобождает**.

### Метрики

Собрать:

* RSS / heap used / heap committed;
* GC frequency, GC pause, promoted objects;
* allocation rate;
* number of threads/goroutines/tasks;
* open file descriptors;
* connection pools;
* queue depth;
* cache size;
* request rate by endpoint;
* p95/p99 latency;
* error rate;
* deployment/config changes за последние 24 часа.

### Hypothesis prioritization

1. **Недавний релиз** → новая утечка.
2. **Кэш без TTL/limit** → рост 6 часов похож на накопление.
3. **Очередь/буфер не очищается** → backlog.
4. **Connection/session leak**.
5. **Большие объекты в памяти**: файлы, JSON, images, ML tensors.
6. **GC pressure**: объекты живут дольше ожидаемого.

### Пошаговый план

1. Зафиксировать инцидент: время начала роста, версия, traffic pattern.
2. Снять heap dump до рестарта.
3. Если можно — снять второй heap dump через 10–15 минут и сравнить.
4. Проверить top retainers: кто удерживает память.
5. Включить profiler: allocation flamegraph.
6. Сравнить endpoints по allocation rate.
7. Проверить caches/maps/queues.
8. Проверить изменения релиза.
9. Временно ограничить ущерб: scale out, restart policy, reduce traffic, disable feature flag.
10. Написать regression test/load test, воспроизводящий рост.

### Инструменты

* JVM: JFR, VisualVM, Eclipse MAT, jmap.
* Node.js: heap snapshots, Clinic.js, Chrome DevTools.
* Python: tracemalloc, objgraph, memray.
* Go: pprof.
* Kubernetes: Prometheus, Grafana, kubectl top, OOMKilled events.

## 156. DB query 30 секунд, seq scan

### Стратегия 1 — Индексы

Если запрос фильтрует:

```sql
WHERE tenant_id = ? AND created_at >= ?
```

Добавить:

```sql
CREATE INDEX idx_orders_tenant_created
ON orders (tenant_id, created_at);
```

**Плюсы:** быстро, минимальная архитектурная цена.
**Минусы:** дороже write, больше storage, индекс может не использоваться при плохой селективности.

### Стратегия 2 — Денормализация / materialized view

Если запрос агрегирует тяжёлые joins:

```sql
CREATE MATERIALIZED VIEW monthly_sales AS ...
```

**Плюсы:** быстрые чтения.
**Минусы:** stale data, refresh complexity, риск рассинхрона.

### Стратегия 3 — Архитектурное разделение

Для аналитики вынести read workload:

```text
OLTP DB → CDC → ClickHouse/BigQuery/Elastic
```

**Плюсы:** не убивает основную БД.
**Минусы:** eventual consistency, новая инфраструктура, дороже ops.

## 158. CI/CD pipeline для Kubernetes

### Stages

```text
lint → unit tests → build image → SAST/SCA/secret scan
→ integration tests → container scan → push image
→ deploy staging → e2e/perf smoke
→ blue-green deploy prod
→ monitor SLO
→ auto rollback
```

### GitHub Actions пример

```yaml
name: service-ci-cd

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test-build-scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up runtime
        uses: actions/setup-node@v4
        with:
          node-version: "20"

      - name: Install deps
        run: npm ci

      - name: Lint
        run: npm run lint

      - name: Unit tests
        run: npm run test:unit

      - name: Integration tests
        run: npm run test:integration

      - name: Secret scan
        run: npx gitleaks detect --no-git -v

      - name: SAST
        run: npm audit --audit-level=high

      - name: Build image
        run: docker build -t registry.example.com/service:${{ github.sha }} .

      - name: Container scan
        run: trivy image --exit-code 1 --severity HIGH,CRITICAL registry.example.com/service:${{ github.sha }}

      - name: Push image
        if: github.ref == 'refs/heads/main'
        run: |
          docker login registry.example.com -u "$REGISTRY_USER" -p "$REGISTRY_PASS"
          docker push registry.example.com/service:${{ github.sha }}

  deploy-staging:
    needs: test-build-scan
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - name: Deploy staging
        run: helm upgrade --install service ./chart --set image.tag=${{ github.sha }} --namespace staging

      - name: E2E tests
        run: npm run test:e2e

      - name: Performance smoke
        run: npm run perf:smoke

  blue-green-prod:
    needs: deploy-staging
    runs-on: ubuntu-latest
    steps:
      - name: Deploy green
        run: helm upgrade service-green ./chart --set image.tag=${{ github.sha }} --namespace prod

      - name: Health gate
        run: ./scripts/check-slo.sh

      - name: Switch traffic
        run: ./scripts/switch-traffic.sh green

      - name: Rollback on SLO failure
        if: failure()
        run: ./scripts/switch-traffic.sh blue
```

### Gates

* tests must pass;
* no critical CVEs;
* no secrets;
* image signed;
* staging e2e pass;
* p95 latency and error rate within SLO.

```python
def factorial(n: int) -> int:
    if n < 0:
        raise ValueError("n must be non-negative")
```

# 550 · Architecture review: e-commerce монолит 100k строк

## Вердикт

Монолит 100k строк сам по себе не преступление. Проблема начинается, если он мешает релизам, масштабированию, изоляции ошибок и владению доменами.

Цена честности: **не надо “микросервисить всё”**. Нужен управляемый strangler roadmap вокруг бизнес-инвариантов: заказ, оплата, склад, каталог, доставка.

---

## 5 критических проблем

### 1. Смешаны доменные границы

**Симптомы:**

* order logic вызывает inventory, payment, email напрямую;
* нет явного ownership по модулям;
* изменение скидки ломает checkout.

**Риск:** любое изменение становится системным. Команда боится релизов.

**Исправление:**

```text
Catalog
Cart
Checkout/Order
Payment
Inventory
Shipping
Notification
Customer
```

Сначала выделить bounded contexts на уровне кода, даже внутри монолита.

---

### 2. Shared database как единая точка связанности

**Симптомы:**

* все модули читают/пишут все таблицы;
* нет владельца таблиц;
* отчёты и checkout конкурируют за одну БД;
* миграции опасны.

**Риск:** невозможно отделить сервис без ломки данных.

**Исправление:**

* назначить table ownership;
* запретить новые cross-domain joins;
* вводить read models;
* CDC/outbox для событий;
* потом database-per-service только для выделенных сервисов.

---

### 3. Checkout не изолирован как критический путь

**Симптомы:**

* падение recommendations/search/email влияет на оформление заказа;
* синхронные вызовы внешних API без timeout/circuit breaker;
* retry может создать дубль заказа/платежа.

**Риск:** потеря денег и доверия.

**Исправление:**

* checkout priority path;
* idempotency keys;
* payment state machine;
* circuit breaker;
* async notifications;
* order saga.

---

### 4. Релизы медленные и рискованные

**Симптомы:**

* один deploy всего монолита;
* слабые тесты;
* ручной regression;
* нет feature flags;
* DB migrations блокируют релиз.

**Риск:** business continuity под угрозой при каждом изменении.

**Исправление:**

* CI gates;
* smoke/e2e для checkout;
* feature flags;
* expand-migrate-contract для БД;
* canary/blue-green, если infra позволяет.

---

### 5. Наблюдаемость недостаточна

**Симптомы:**

* есть logs, но нет correlation id;
* непонятно, где падает order;
* нет SLO по checkout/payment;
* инциденты тушатся “на глаз”.

**Риск:** система ломается раньше, чем команда понимает причину.

**Исправление:**

* structured logs;
* distributed tracing;
* metrics по доменам;
* SLO: checkout success, payment authorization latency, order confirmation correctness;
* alerting по burn rate.

---

## Roadmap миграции к микросервисам без остановки бизнеса

### Phase 0 — Stabilize before splitting

**Цель:** сделать монолит безопасным для разрезания.

Действия:

1. Добавить observability: logs, metrics, traces, correlation id.
2. Покрыть checkout smoke/e2e тестами.
3. Ввести feature flags.
4. Зафиксировать ownership таблиц.
5. Запретить новые cross-domain зависимости.

**Exit criteria:**

```text
checkout smoke test автоматизирован
есть dashboard checkout/payment/order
есть список domain boundaries
есть rollback plan
```

---

### Phase 1 — Modular monolith

**Цель:** сначала отделить модули внутри одного deploy.

```text
monolith/
  catalog/
  cart/
  checkout/
  payment/
  inventory/
  shipping/
  notification/
```

Правила:

* модули общаются через interfaces;
* нет прямого доступа к чужим таблицам;
* domain events внутри процесса;
* repositories принадлежат доменам.

**Почему так:** если команда не может держать границы в монолите, микросервисы только добавят сеть к хаосу.

---

### Phase 2 — Extract low-risk services first

Не начинать с checkout/payment. Начать с:

1. **Notification service** — email/SMS/push.
2. **Search service** — Elasticsearch/OpenSearch read model.
3. **Recommendation service** — может graceful degrade.
4. **Catalog read API** — если heavy reads.

**Почему:** эти сервисы можно уронить без потери заказов.

---

### Phase 3 — Introduce event backbone

Добавить:

```text
Transactional Outbox → Kafka/Pulsar/RabbitMQ → Consumers
```

События:

```text
OrderCreated
PaymentAuthorized
InventoryReserved
OrderConfirmed
OrderCancelled
ShipmentCreated
```

Правило: событие публикуется надёжно вместе с DB transaction через outbox, а не “после commit в надежде, что не упадёт”.

---

### Phase 4 — Extract Inventory

**Почему inventory рано или поздно должен стать автономным:** там конкуренция за stock, reservation, oversell risk.

Нужны инварианты:

```text
reserved + sold <= available
reservation has TTL
release reservation on cancel/timeout
idempotent reservation commands
```

Checkout пока может оставаться в монолите, вызывая Inventory service через clear API.

---

### Phase 5 — Extract Payment carefully

Payment — high-risk.

Требования:

* idempotency keys;
* state machine: `INITIATED → AUTHORIZED → CAPTURED / FAILED / REFUNDED`;
* webhook deduplication;
* reconciliation jobs;
* audit log;
* circuit breaker.

Не делать payment extraction без тестов и rollback.

---

### Phase 6 — Extract Order / Checkout last

Order/Checkout — сердце e-commerce. Выносить после того, как inventory/payment/notification уже имеют чёткие контракты.

Использовать Saga:

```text
CreateOrder
→ ReserveInventory
→ AuthorizePayment
→ ConfirmOrder
→ CapturePayment
→ NotifyCustomer
```

Compensation:

```text
payment failed → release inventory
inventory failed → cancel order
capture failed → manual/retry/reconciliation
```

---

## Business continuity guardrails

| Риск                     | Защита                                   |
| ------------------------ | ---------------------------------------- |
| Новый сервис падает      | fallback в legacy path, feature flag off |
| События теряются         | transactional outbox + retry + DLQ       |
| Данные расходятся        | reconciliation jobs + audit reports      |
| Latency растёт           | circuit breaker + bulkheads + cache      |
| Миграция БД ломает релиз | expand-migrate-contract                  |
| Команда не успевает      | extract one domain at a time             |
| Customer impact          | canary by tenant/region/percent traffic  |

# 551–554 · Engineering / reliability

## 551. Система тормозит: диагностика bottleneck

**Verdict: PARTIAL** — логи/метрики/код не приложены, поэтому bottleneck нельзя честно назвать. Правильный план:

1. **Стабилизировать:** проверить error rate, p95/p99 latency, saturation CPU/RAM/IO/DB connections, queue depth.
2. **Сегментировать:** какой путь тормозит — frontend, API, DB, external API, queue worker, cache.
3. **Trace:** включить distributed tracing с correlation id; найти самый дорогой span.
4. **Profile:** CPU profile, heap profile, allocation profile, flamegraph.
5. **DB:** slow queries, query plan, locks, seq scans, missing indexes, connection pool exhaustion.
6. **Код:** hot path, blocking I/O, N+1, unbounded loops, serialization, cache misses.

**Три решения с trade-offs:**

| Вариант                     | Когда                | Плюс                    | Цена                                      |
| --------------------------- | -------------------- | ----------------------- | ----------------------------------------- |
| Индексы/SQL rewrite         | bottleneck в БД      | быстро, дешево          | дороже writes, риск неправильного индекса |
| Кэш/read model              | частое чтение        | снижает latency         | invalidation, stale data                  |
| Async/background processing | долгий sync workflow | разгружает request path | eventual consistency, retry/idempotency   |

**Verify:** до/после сравнить p95 latency, DB time, error rate, throughput, resource saturation.

## 552. Legacy codebase: god classes, circular deps, no tests

**Roadmap strangler fig:**

1. **Freeze damage:** запретить большие переписывания без тестов.
2. **Characterization tests:** зафиксировать текущее поведение legacy flows.
3. **Find seams:** HTTP endpoints, CLI commands, DB repositories, payment/email/file adapters, scheduled jobs.
4. **Dependency map:** найти циклы и hot spots.
5. **Modularize first:** выделить domain modules внутри монолита.
6. **Anti-corruption layer:** новый код не должен тащить legacy DTO и global state.
7. **Extract low-risk modules:** notifications, reporting, search, imports/exports.
8. **Data migration:** table ownership → outbox/CDC → backfill → dual-read/dual-write → cutover.
9. **Kill old paths:** только после traffic=100% new, tests pass, data reconciled.

**Приоритет:** безопасность/payment/auth → high-change modules → modules with clear seams → low-risk async services.

## 553. System design: URL shortener / Twitter / Uber / WhatsApp

**Verdict: PARTIAL** — это четыре разные system-design задачи. Дам универсальный каркас + deep dive для URL shortener.

### Универсальный каркас

| Система       | Главное узкое место                                             |
| ------------- | --------------------------------------------------------------- |
| URL shortener | read-heavy redirects, low latency, abuse prevention             |
| Twitter/X     | fanout, feed ranking, hot users                                 |
| Uber          | geospatial matching, realtime location, surge/pricing           |
| WhatsApp      | low-latency messaging, delivery state, encryption, offline sync |

### Deep dive: URL shortener

**Capacity:** 100M redirects/day, 1M new URLs/day. Read/write ≈ 100:1.
**API:**

```http
POST /v1/links { "long_url": "...", "custom_alias": optional }
GET /{short_code} -> 301/302 redirect
GET /v1/links/{id}/stats
```

**Data model:**

```text
links(id, short_code, long_url, owner_id, created_at, expires_at, status)
clicks(short_code, timestamp, country, referrer, user_agent_hash)
```

**Architecture:**

```text
Client → CDN/WAF → API Gateway
  → Link Service → DB
  → Redirect Service → Redis cache → DB fallback
  → Analytics Queue → Stream processor → OLAP
```

**Deep components:**

* **Code generation:** base62 counter, random slug, or hash+collision check.
* **Redirect path:** cache hot short_code in Redis/CDN; DB only fallback.

**Trade-offs:**
301 faster/cached, but hard to change destination. 302 flexible, more load. Random IDs avoid enumeration but need collision handling.

| 634 | Муравейник умнее муравья из-за **распределённого интеллекта**: простые правила, локальные сигналы, феромоны, обратная связь. Нет “главного мозга”, но есть коллективная обработка информации.                                                    |

# 709–713 · Системное мышление

## 709. Causal loop diagram: общественный транспорт теряет пассажиров

```text
R1: Пассажиры ↓ → выручка ↓ → частота рейсов ↓ → ожидание ↑ → качество ↓ → пассажиры ↓

R2: Пассажиры ↓ → политическая поддержка ↓ → инвестиции ↓ → качество инфраструктуры ↓ → пассажиры ↓

R3: Пассажиры ↓ → больше людей на авто ↑ → пробки ↑ → автобусы медленнее ↓ → привлекательность транспорта ↓ → пассажиры ↓

B1: Пробки ↑ → спрос на альтернативы авто ↑ → интерес к транспорту ↑ → пассажиры ↑

B2: Пассажиры ↓ → загруженность транспорта ↓ → комфорт ↑ → часть пассажиров возвращается ↑

B3: Субсидии/инвестиции ↑ → частота рейсов ↑ → ожидание ↓ → пассажиры ↑ → потребность в субсидиях ↓
```

**Leverage points:** выделенные полосы, приоритет светофоров, частота в часы пик, интеграция тарифов, надёжность расписания, park-and-ride, real-time arrival, безопасность остановок.
Главный рычаг: **надёжность + скорость**, а не просто реклама.

## 711. Hospital emergency overcrowding

Не симптоматические fixes:

1. **Patient flow redesign:** triage → fast-track minor cases → observation unit → discharge planning.
2. **Bed management:** real-time bed visibility, early discharge rounds, discharge lounge.
3. **Upstream care:** urgent care clinics, teletriage, chronic care support.
4. **Downstream capacity:** social care, rehab, transport home, pharmacy delays.
5. **Queue theory:** держать utilisation ниже 100%; иначе ожидание растёт нелинейно.
6. **Metrics:** door-to-triage, left-without-being-seen, boarding time, bed turnover, nurse ratio.

Главная мысль: переполненный ED часто не проблема ED, а симптом всей hospital flow system.

## 712. Почему “дать денег” против бедности часто не работает

Нюанс: денежные трансферы **могут работать**, особенно когда проблема — liquidity constraint. Не работает “часто” там, где бедность поддерживается системой:

* дорогая медицина/жильё/долги съедают трансфер;
* локальные цены растут;
* benefits cliff: человек теряет пособия при малом росте дохода;
* нет доступа к работе, транспорту, детсадам, образованию;
* dependency trap, если программа наказывает за инициативу;
* коррупция/посредники;
* локальная оптимизация: помощь одному домохозяйству без изменения рынка труда.

Системное решение: cash + услуги + инфраструктура + incentives + снятие cliffs + human capital + local jobs.

## 713. Почему agile-фреймворки проваливаются

Потому что Scrum/Kanban поверх старой системы не меняет причинные петли:

* команды не автономны;
* релизы всё равно через комитет;
* KPI на занятость, а не value;
* ошибки караются → нет transparency;
* product owner без полномочий;
* зависимости между командами не сняты;
* backlog превращён в список приказов.

Agile — не церемонии. Это система короткой обратной связи, автономии и learning loop.

```yaml
        "201": { description: Loan created }
        "409": { description: No copies available or member blocked }

  /loans/{loan_id}/return:
    post:
      summary: Return a book
      responses:
        "200": { description: Returned }

components:
  schemas:
    BookCreate:
      type: object
      required: [title, isbn]
      properties:
        title: { type: string }
        isbn: { type: string }
        author_ids:
          type: array
          items: { type: string }
        published_at: { type: string, format: date }
```

**Edge cases:** duplicate ISBN, deleted book with active loan, lost copy, overdue member, idempotent retry, page overflow, unsupported sort field.

|   № | Ответ                                                                                                                                                                                                                                  |
| --: | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 715 | **GraphQL vs REST:** REST лучше для простых resource APIs, caching, public APIs. GraphQL лучше, когда клиенты разные и нужен точный shape данных. Минусы GraphQL: сложнее caching, auth per field, query cost control.                 |
| 716 | **Webhooks vs polling:** webhooks быстрее и дешевле, но требуют публичный endpoint, retry, signature verification. Polling проще, но шумный и задержанный.                                                                             |
| 717 | **Versioning:** URL `/v1`, header `API-Version`, content negotiation. URL проще для клиентов; header чище, но менее очевиден. Главное — backward compatibility и deprecation policy.                                                   |
| 718 | **Rate limiting/backoff:** token bucket/sliding window; ответы `429` + `Retry-After`. Backoff: exponential + jitter, max attempts, idempotency.                                                                                        |
| 719 | **OAuth2:** resource owner authorizes client; client gets authorization code; exchanges code for access token; uses token for API. For public clients — PKCE.                                                                          |
| 720 | **API keys vs JWT vs mTLS:** API key identifies app, weak for user auth. JWT carries claims, good for stateless auth but needs expiry/revocation plan. mTLS strongly authenticates services/machines.                                  |
| 721 | **Idempotency POST:** client sends unique key; server stores request hash and response; retry returns same result, preventing duplicate order/payment.                                                                                 |
| 722 | **Pagination:** offset simple but slow/unstable on large changing data. Cursor stable and efficient, needs deterministic ordering.                                                                                                     |
| 723 | **HATEOAS:** pros — discoverability, decoupling; cons — verbosity, client complexity, weak adoption. Useful for hypermedia-heavy APIs, often overkill for internal APIs.                                                               |
| 724 | **gRPC vs REST:** gRPC for internal low-latency typed service-to-service, streaming. REST for browser/public/simple APIs.                                                                                                              |
| 725 | **Async APIs:** webhooks, callbacks, polling, event streams. Use when result is delayed: payments, exports, ML jobs.                                                                                                                   |
| 726 | **API Gateway:** auth, routing, rate limits, request validation, transformation, caching, analytics, circuit breaking. Не класть туда core business logic.                                                                             |
| 727 | **Service mesh:** sidecars/proxies manage mTLS, retries, traffic splitting, observability, policies. Istio = control plane + data plane.                                                                                               |
| 728 | **Event-driven APIs:** webhooks for external consumers; Kafka/Pulsar for internal streams. Need schema registry, idempotency, ordering, DLQ.                                                                                           |
| 729 | **OpenAPI docs:** schema, endpoints, auth, examples, errors, rate limits, idempotency, changelog. Docs must be generated/tested against contract.                                                                                      |
| 730 | **Contract testing:** consumer expectations verified against provider; prevents breaking API changes. Tools: Pact-style workflows.                                                                                                     |
| 731 | **API monetization:** freemium, usage-based, tiered quotas, revenue share, enterprise SLA, marketplace. Need metering and billing accuracy.                                                                                            |
| 732 | **Third-party adapter:** isolate vendor-specific DTO/auth/errors behind interface. Add retries, circuit breaker, mapping, observability, sandbox tests.                                                                                |
| 733 | **OWASP API security:** broken object auth, broken auth, excessive data exposure, rate limit gaps, mass assignment, injection, SSRF, misconfig, inventory gaps. Mitigate with object-level auth, schemas, allowlists, least privilege. |

# 734–753 · Data systems

|   № | Ответ                                                                                                                                                                                                              |

| 734 | **SQL:** JOINs combine tables; window functions compute over partitions without collapsing rows; CTEs improve readability and reuse. Example: `ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC)`. |

# 789–793 · Финальные system design задачи

## 789. E-commerce + legacy ERP SOAP/batch + modern CRM REST/realtime

```text
E-commerce Platform
   |
   v
Integration API / BFF
   |
   v
Message Bus / Queue  <---->  Transformation Layer / Canonical Model
   |                               |
   |                               +--> ERP Adapter: SOAP + batch files
   |                               +--> CRM Adapter: REST + webhooks
   |
   +--> Error Queue / DLQ
   +--> Reconciliation Service
   +--> Audit Log / Data Lake
```

**Principles:**

* Canonical model: `Customer`, `Order`, `Invoice`, `Shipment`, `PaymentStatus`.
* ERP через async integration: batch windows, SOAP retries, idempotent document IDs.
* CRM near real-time: customer events, lead updates, lifecycle status.
* Message queue сглаживает разницу скоростей.
* Transformation layer отделяет e-commerce от XML/SOAP quirks.
* Reconciliation: daily compare orders/invoices/payments across systems.
* Error handling: retry transient, DLQ permanent, manual repair UI.
* Observability: correlation id from order to ERP document to CRM record.

**Edge cases:** ERP недоступен, CRM принимает дубль, batch частично обработан, изменение заказа после отправки, разные enum/status models.

## 790. Pipeline 1TB/day

```text
API Ingestion
  → Raw Object Storage
  → Schema Validation
  → Quarantine Bad Records
  → Transformation
  → Warehouse Load
  → Data Quality Checks
  → BI/Analytics
  → Monitoring/Lineage
```

**Tech stack:**

* Ingestion: Kafka/Pulsar or managed streaming.
* Raw: S3/GCS/Blob, partitioned by date/source.
* Schema: Avro/Protobuf/JSON Schema + registry.
* Transform: Spark/Databricks/dbt depending batch/ELT.
* Warehouse: BigQuery/Snowflake/Redshift.
* Orchestration: Airflow/Prefect.
* Quality: Great Expectations/Soda-style checks.
* Monitoring: freshness, volume, schema drift, failure rate, SLA.

**Schema evolution:** backward-compatible fields, default values, versioned schemas, contract tests.
**Backfill:** replay raw partitions by date with idempotent writes.
**GDPR deletion:** maintain subject index, delete/anonymize in warehouse, lake, derived marts; log deletion proof.

## 791. CI/CD для 50 разработчиков

**Branch strategy:** trunk-based development, short-lived feature branches, PR review, feature flags.
**Pipeline:**

```text
PR:
  lint → typecheck → unit tests → SAST/SCA → build
Merge to main:
  integration tests → container build/sign → staging deploy → e2e
Release:
  canary/blue-green → SLO gate → promote/rollback
```

**Testing pyramid:**

* many unit tests;
* contract tests for services;
* integration with testcontainers;
* limited e2e on critical flows;
* performance smoke for hot paths.

**Secrets:** OIDC to cloud, no static secrets, vault/secret manager, masked logs.
**Rollback:** previous image, DB backward-compatible migrations, feature flag kill switch.
**Governance:** CODEOWNERS, required checks, release notes, incident rollback owner.

## 792. API Gateway для 100 микросервисов

```text
Clients
  |
  v
Edge WAF/CDN
  |
  v
API Gateway Cluster
  |-- AuthN/AuthZ
  |-- Rate limit per client/tenant/route
  |-- Request validation
  |-- Request/response transformation
  |-- Caching
  |-- Circuit breaking
  |-- Analytics/metering
  |-- Correlation IDs
  |
  v
Service Mesh / Internal Services
```

**Unified auth:** OAuth2/OIDC, JWT validation, scopes/claims, tenant isolation.
**Rate limiting:** token bucket per client, per route, per tenant; global abuse limits.
**Transformation:** external DTO ↔ internal APIs; versioning support.
**Caching:** only safe GETs, vary by auth/tenant/locale.
**Circuit breaker:** protect downstream, fallback where possible.
**Analytics:** request count, latency, error rate, quota, billing usage.
**Anti-pattern:** gateway as “mega-service” with business logic.

## 793. Monitoring distributed system

```text
Services
  | emit
  +--> Metrics: Prometheus
  +--> Logs: ELK/Loki
  +--> Traces: OpenTelemetry → Jaeger/Tempo/Zipkin
  |
Alerting: Alertmanager/PagerDuty
Dashboards: Grafana
Runbooks: linked per alert
```

**Correlation:**

* every request gets `correlation_id` / `trace_id`;
* logs include service, version, env, tenant, route, error_code;
* traces connect spans across services;
* metrics use controlled labels to avoid cardinality explosion.

**SLO monitoring:**

* define SLI: availability, latency, correctness, freshness.
* SLO: e.g. checkout success 99.9%, p95 latency < 500ms.
* alert on burn rate, not random CPU spikes.

**Reducing alert fatigue:**

* alert only actionable symptoms;
* route by ownership;
* deduplicate related alerts;
* severity tiers;
* maintenance windows;
* auto-silence known deploy noise;
* postmortem every noisy alert.

**Runbooks:**

Each alert includes:

```text
Meaning:
Impact:
First checks:
Dashboards:
Logs query:
Rollback:
Escalation:
Known false positives:
```

**Critical dashboards:** golden signals — latency, traffic, errors, saturation; plus business metrics: orders, payments, failed jobs, queue lag.
