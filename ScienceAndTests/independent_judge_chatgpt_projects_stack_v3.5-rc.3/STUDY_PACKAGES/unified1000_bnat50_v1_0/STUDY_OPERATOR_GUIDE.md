# Study Operator Guide — Unified-1000/BNAT-50 с Independent Judge v3.5-rc.3

Написано для оператора без ИТ-опыта. Технические термины поясняются по ходу.

## Что это за пакет

Банк из 1000 задач, внутри которого на 50 позициях спрятаны специальные проверочные случаи (BNAT: 18 канонических + 32 замаскированные мутации). Три файла в `aimodels/` — это ответы трёх разных моделей, снятые с банка **версии v1.0**. ВНИМАНИЕ: 126 заданий были усилены в v1.1 (список — `evaluator_private/answer_staleness_v1_1.json`); для этих позиций старые ответы НЕ соответствуют новому вопросу и должны быть перегенерированы до оценки. Валидны без перегенерации только 874 позиции. Судья сравнивает эти ответы по своему протоколу, не зная, какая модель какая.

## Роли файлов (что куда можно загружать)

| Папка/файл | Кому видна | Зачем |
|---|---|---|
| `candidate/unified_1000_questions_tasks_bnat50_v1_1.md` | кандидату (модели, которая отвечает) | активный банк задач (v1.0 архивирован в `versions/`) |
| `aimodels/модель1..3_answers_001_1000.md` | судье (как candidate outputs) | ответы для оценки, под нейтральными метками |
| `evaluator_private/` | ТОЛЬКО оператору, вне Project судьи | «ключи»: где спрятаны BNAT-задачи, какая модель какая |
| `audit/`, отчёты QC | оператору; судье — после commit verdict | проверка целостности банка |

Простое правило: всё, что раскрывает «где спрятаны проверки» или «кто есть кто», судья не видит до того, как зафиксирует вердикт. Это как экзамен: у проверяющего нет списка «какие вопросы с подвохом» до конца проверки — иначе проверка нечестная.

## Пошаговый протокол study-run

1. **Свежий Project.** Для строгого blind-режима создай новый одноразовый ChatGPT Project (не переиспользуй старый — память Project видит прошлые чаты внутри него).
2. **Ядро судьи.** Вставь Project Instructions, загрузи 30 файлов Knowledge (пачками по 10).
3. **Расширения режима.** В свободные слоты добавь `EXT31_STUDY_AGGREGATION.md` (агрегация) и для blind — `EXT33_BLIND_WORKFLOW.md`.
4. **Нейтральные метки.** Для STRICT_BLIND ручное назначение меток ЗАПРЕЩЕНО (оператор помнит исходный порядок — утечка). Вне Project судьи прогони skill `judge-blind-workflow`: модель1/2/3 → случайные метки (например K/L/M). Sealed identity manifest храни у себя, вне любого Project судьи; в reserved slots Project загружай только нейтрализованные candidate-файлы, не mapping.
5. **Кандидатские ответы.** Переименуй файлы ответов в нейтральные метки и загрузи в Project судьи вместе с candidate-файлом банка.
6. **Прогон.** Судья работает батчами задач (размер батча фиксируй заранее); каждый ответ — отдельный run со статусами; hard-fail не усредняется.
7. **Агрегация.** По EXT31: средние только по валидным runs, доля hard failures отдельно, winner=null без зарегистрированного метода сравнения и swap-контроля.
8. **Commit verdict → unblind.** Только после фиксации вердикта раскрой соответствие меток и сверь с `evaluator_private/`.
9. **Receipt.** Сохрани отчёт: версия банка (sha256 candidate-файла — в `audit/qc_summary.json`), версия протокола судьи, дата, модель судьи, статусы.

## Ограничения честности (claim ceiling)

- **Hard stop:** нельзя оценивать все 1000 старых ответов против v1.1 — 126 позиций устарели. Сначала перегенерируй ответы для них.
- Результат по умолчанию `DIAGNOSTIC_ONLY`: это диагностика, не «научно доказанный рейтинг моделей».
- 18 канонических BNAT-задач публичны и могли попасть в обучение моделей — сильные выводы строй только на 32 приватных мутациях и контролируемых повторных прогонах.
- «Модель X лучше всех» без blind, swap-контроля и повторных прогонов — запрещённый claim (L3 максимум, см. EXT31).
